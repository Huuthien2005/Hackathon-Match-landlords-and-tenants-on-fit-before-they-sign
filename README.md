# Deservia match engine (Brampton AI Innovator, Challenge 9)

Lifestyle matching for landlords and tenants: "We match on how you live, never on who you are."
Made-up data only.

## Run it

```bash
pip install -r requirements.txt
python server.py              # or: uvicorn api:app --reload   (API docs at /docs)
```
Open http://127.0.0.1:8000 and sign in. Demo accounts are created on first start:

## Deploy (Render, free plan)

The repo includes `render.yaml`, `.python-version` (3.13.5) and pinned `requirements.txt`
(scikit-learn 1.9.1, the version the model was saved with). Production runs `server.py` (fully tested);
it uses ~170 MB of memory (free plan: 512 MB).

1. Keep the database out of Git (it holds accounts): `git rm --cached data/deservia.db`, commit, push.
   The server rebuilds it from the CSVs on start.
2. On render.com: **New → Blueprint**, pick this GitHub repo, **Apply**.
3. Wait for the build (a few minutes), open `https://<name>.onrender.com`.
4. The owner password is generated by Render: service → **Environment** → `DESERVIA_ADMIN_PASSWORD` → reveal.

Production settings (`render.yaml`): `HOST=0.0.0.0`, `DESERVIA_PUBLIC_DEMO=1` (banner: made-up data only;
owner login hidden on the sign-in page), `DESERVIA_RESET_ON_START=1` (each start has only the demo accounts),
random `DESERVIA_ADMIN_PASSWORD`. Sign-in locks for 10 minutes after 8 wrong passwords per email.

**Free-plan limits:** the app sleeps after 15 minutes idle and takes 30–60 s to wake (open it a few minutes
before the pitch); the disk is temporary, so new sign-ups and swipes are lost on restart. For real users:
a paid instance with a persistent disk or Postgres, a lawyer-reviewed privacy policy, encryption at rest,
and Stripe/SingleKey connections, as Deservia's own policy requires.

## Membership (10 free matches, then subscribe)

Every tenant and landlord gets **10 free matches**. After the first 10 flashcards, "Show my next 10" opens the
membership plans: tenants see Tenant Silver, landlords see Landlord Gold and Platinum. The server enforces it
(`deservia/plans.py`, `routes._need_matches_left`): the deck and swipe endpoints return **402** with the plans
once the free matches are used. **Subscribe is a demo checkout: no card, no payment**; Stripe replaces it in the
build phase. Users see their plan on the swipe page and can cancel it (demo) in My answers. The owner sees
each user's plan and a "Paid members" count. To re-test, cancel the plan in My answers and use the owner's
"Reset all swipes".

## Three sides

**Tenants and landlords** create an account (right after the questionnaire, a new account sees its first 10
flashcards, same as an existing one; landlords in areas with few tenants in the data, like Hamilton or a typed-in
city, are matched against all tenants so there are always cards), (email + password, 8+ characters), answer the questionnaire one
question per screen (same look as Deservia's onboarding), then swipe 10 flashcards at a time on a centred swipe page. They see the
match %, things in common, lifestyle tags, and *their own* phrases that weren't used. They never see AI
scores, the audit or metrics: the server strips them (`routes._public_card`). When both sides ♥ each other
it's a **mutual match**, and "My matches" says the agent will reach out to book a viewing.

**Typing your own answer.** Every choice question has "✏️ Other: type your own", hobbies have "Add your own",
and the area box accepts any city or neighbourhood. A typed answer that clearly means an option is matched to it
and scored ("I wake up at 5am" → Early riser, "condo" → Apartment, "driveway fits 2 cars" → 2+ spots). One that
doesn't is kept on the profile but not scored, so the match % stays explainable. Typed hobbies count as written
("Pickleball" matches "Pickleball"). A typed answer that describes *who someone is* ("Muslim household",
"no kids") is refused with a request to rephrase, so it is never stored. **My answers** shows every answer,
typed text in purple, and how it's used ("Matched as 🌅 Early riser" / "not used for the match score").
Rules live in `deservia/questionnaire.py` (`SYNONYMS`, `match_option`, `apply_other`, `describe`).

**The agent (website owner)** gets a console: Overview (users, swipes, like rate, *do higher match scores get
more likes?*, liked-vs-passed averages, mutual matches ready for viewings, AI model status with Retrain
button, and protected-ground phrases users wrote), Users (per-user swipes, likes, mutual matches, learned
preferences), Fairness audit, AI model, Launch metrics, and the Rules demo for Sunday's two demo items.
Agent accounts can't be created through sign-up.

**Deservia's privacy promises, built in:** sign-up requires ticking *I'm 18 or older* and *I agree to the Privacy
Policy* (the consent time is recorded); **Delete my account** (My answers, password required) removes the account,
answers, swipes, everyone's swipes on that person and all sessions, and takes them out of the matching pool
(PIPEDA right to deletion); **Withdraw** (My matches) lets either side take back a like at any time, so a mutual
match stops being mutual.

**Security and privacy:** passwords are hashed (PBKDF2-SHA256, 200k iterations, per-user salt); sessions
are random tokens that expire after 7 days; every route checks the caller's role (`deservia/routes.py`);
questionnaire answers are validated on the server against the allowed options, so extra fields like `diet`
are dropped; landlords never see a tenant's name, service-animal status, or what the tenant wrote that was
excluded. The questionnaire doesn't ask diet, work situation or daytime-at-home at all.

## How a score is made

1. **Hard filters**: rent more than 10% over budget, too few bedrooms, a pet the policy doesn't allow
   (a service animal is never a pet), a smoker in a non-smoking home, or any criterion the user marked
   "dealbreaker". Filtered listings are listed with a reason, not hidden.
2. **Criteria**: each scores 0–1: budget, area, rental type, timing, parking, smoking, pets, tidiness,
   noise, early/night, introvert/extrovert, hobbies, travel, cooking smells (shared kitchens only),
   repair speed, and the "ideal tenant/landlord" words checked against the other side's real answers.
3. **Two-way percent** = √(tenant-side × landlord-side) × 100. Each side is weighted by *its own*
   importance levels, so the percent is "the criteria both sides set". The geometric mean means a match
   has to work for both sides.
4. **Explanation**: "things in common" (lifestyle first) and a per-criterion breakdown ("Why 95%?").

## Fairness guard

| Layer | What it does | Where |
|---|---|---|
| Allowlist | Only lifestyle and home fields can reach the scorer | `fairness.SCORED_FIELDS` |
| Never scored | diet, work, days, service animal, name, with the reason for each | `fairness.NOT_SCORED` |
| Text filter | Protected-ground phrases ("no kids", "no ODSP", "Christian household") are removed and shown | `fairness.check_text` |
| Audit | Hidden group never seen by the scorer; four-fifths rule, safe vs "also scoring diet/work/days" | `audit.py` |

Current result (600 tenants × 100 listings from the dataset): lifestyle-only engine **0.996 ✓**. Also scoring
the live site's diet / work-from-home / work questions: **0.39 ✗**.

## Findings for Deservia's live questionnaire

- **Q8 "How do you eat?"** (vegan/vegetarian…) and the "Pescatarian" card tag: diet can stand in for creed.
  Replace with "cooking smells", as Deservia's own PDF says.
- **Q4 work situation**: no option for people not working, so it can stand in for public assistance. Not scored.
- **Q5 where you spend your days**: can stand in for disability or caregiving. Not scored.
- **Missing questions the brief needs**: monthly budget (the "is it affordable" check), bedrooms, repair-speed
  expectations, the ideal tenant/landlord words, and importance per question.
- **Affordability** uses the tenant's own budget, never a rent-to-income ratio (the OHRC has found those
  discriminatory). Income checks stay with SingleKey.

## Connecting to deservia.netlify.app

CORS is open. The front end can `POST /api/match` with `{"tenant": {...answers...}}` and render each match's
`name, area, rental_type, price, description, match_pct, tags, in_common_count`, which is exactly what its card
shows today. Option ids are in `deservia/options.py`.

## Roadmap (continuing team)

Learn weights from outcomes: the ratings spec's tags ("Paid on time", "Cared for the home", "Quick repairs")
plus accepts and withdrawals become labels for learning-to-rank. Keep the audit as a check before every
release, encrypt questionnaire data at rest, and replace `BASE_RENT` with CMHC Rental Market Survey figures.
